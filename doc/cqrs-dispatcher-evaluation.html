MediatR Alternatives Evaluation

Comparative assessment of open-source mediator, CQRS dispatcher, and message-bus alternatives for the eDMS backend.

Prepared 18 August 2026 Target platform: .NET 10 Decision focus: licensing, maintenance, compatibility, security, and fit

Executive verdict

There is no single best MediatR replacement for eDMS. Mukesh’s dispatcher is a credible custom baseline; Mediator is a strong but conditional source-generated option; Immediate.Handlers is the most interesting source-generated candidate to spike; and OpenMediatR is the lowest-friction API-compatible alternative.

For current eDMS scope, compare Immediate.Handlers, OpenMediatR, and Mediator through one common vertical slice. Keep Wolverine for a future durable-messaging decision, and treat Foundatio.Mediator, DispatchR, ModernMediator, and a custom dispatcher as secondary experiments or ownership-heavy options.

1. Scope and reviewed material

This report evaluates MediatR alternatives for eDMS. It uses the article and its full runnable repository as the custom-dispatcher baseline, then compares that baseline with source-generated mediators, a MediatR-compatible implementation, a broader message bus, and several smaller open-source projects. The focus is not whether CQRS is useful; CQRS and the mediator pattern are separate design choices. The focus is which option preserves eDMS’s production requirements with a sustainable ownership model.

  • Article: Build Your Own CQRS Dispatcher in .NET 10 (No MediatR)
  • Runnable GitHub repository
  • Repository benchmark results

The current eDMS baseline is .NET 10 with MediatR 12.4.1. The relevant integration is in server/src/eDMS.Application/eDMS.Application.csproj and server/src/eDMS.Application/DependencyInjection.cs. The shortlist is assessed against the existing controller, EF Core, validation, authorization, audit, notification, and multi-provider database architecture.

2. Article dispatcher baseline

The implementation replaces MediatR’s request dispatch path with a small in-process dispatcher:

  • At startup, it scans an assembly for request and notification handlers.
  • It creates strongly typed handler wrappers and stores them in a FrozenDictionary<Type, ...>.
  • At request time, it performs a dictionary lookup, resolves the handler from dependency injection, and composes registered pipeline behaviors.
  • It uses ValueTask in the public dispatcher and pipeline contracts.
  • It supports in-process notifications through a lightweight publisher.

The startup path still uses reflection and Activator.CreateInstance; the stated optimization is that the request hot path avoids reflection.

3. Article benchmark interpretation

The repository compares a trivial Ping(string) -> string request across raw method invocation, the custom dispatcher, MediatR 12.4.1, and a reflection-based dispatcher.

Important qualification: the benchmark is valid evidence about dispatcher overhead, but it is not an end-to-end eDMS benchmark. EF Core, permission resolution, recursive authorization queries, file storage, audit persistence, authentication, serialization, and network latency will normally dominate the numbers above.

The custom dispatcher still resolves the scoped handler and pipeline behaviors through DI on each request. FrozenDictionary removes a type/reflection lookup cost; it does not make the complete use-case execution allocation-free.

4. Article dispatcher strengths

Small and understandable

The core is compact enough for a team to inspect, debug, and own. There is no opaque remote transport or distributed protocol hidden behind the abstraction.

Efficient hot path

Startup-time registration plus typed wrappers is a sensible way to remove repeated reflection from a high-throughput in-process API.

Explicit behavior composition

Validation, logging, caching, and transactions are represented as ordinary pipeline behaviors. Registration order is visible and controllable.

Clear boundary

The article correctly explains that this is an in-process dispatcher, not a durable message bus. Horizontal API scaling does not by itself require a distributed mediator.

The article also calls out its own limitations: the ValueTask single-consumption rule, the assembly-scan/AOT caveat, and the non-durable behavior of its notification publisher. Those caveats are important evidence that the implementation is not being presented as a complete distributed messaging platform.

5. Article dispatcher risks and limitations

5.1 Security and audit are not included in the sample

The sample includes logging and validation, but no eDMS-equivalent authorization behavior. Every mutating eDMS request must remain server-authorized through the existing permission resolver. The existing AuthorizationBehavior.cs must be ported or replaced with behaviorally identical code.

Likewise, the existing AuditLoggingBehavior.cs implements an eDMS audit policy. Replacing the dispatcher must not weaken immutable audit recording, its timing, or its failure handling.

5.2 The compatibility claim is optimistic for eDMS

The article presents MediatR-like request and pipeline shapes, but the documented handler contract is primarily IRequestHandler<TRequest, TResponse> and the return type changes to ValueTask. eDMS also has no-response commands and many Task-based handlers. This is more than a using-directive swap unless the custom library adds a no-response overload/adaptor or all commands are deliberately migrated.

5.3 Assembly discovery must be precise

The sample’s AddDispatcher(Assembly.GetExecutingAssembly()) works because its handlers are in the API assembly. eDMS handlers live in the Application assembly. The dispatcher must explicitly scan the Application assembly, and startup validation should reject missing or duplicate handlers rather than silently accepting an ambiguous registration.

5.4 ValueTask trade-off

ValueTask can reduce allocations for synchronously completed operations, but it is easier to misuse. The article itself warns that a ValueTask cannot be awaited more than once. Retry or replay behavior must create a fresh pipeline or convert the value to a Task. Since most eDMS handlers perform database or other I/O, the practical benefit is likely small compared with the added discipline.

5.5 Generic transactions are not enough for eDMS

The sample transaction behavior is useful for a simple EF Core application, but a generic transaction around every command cannot make database changes and filesystem/blob writes atomic. eDMS also supports multiple database providers. Transaction policy should remain aligned with each use case and the existing storage/outbox/audit design.

5.6 Notifications are not durable messaging

The sample publisher invokes handlers in-process and sequentially. It does not provide retries, crash recovery, cross-instance delivery, post-commit guarantees, scheduling, or restart survival. It should not replace eDMS’s persisted notification and background-processing paths without preserving idempotency and durable delivery.

5.7 Native AOT is not automatic

Because the default implementation uses assembly reflection and Activator.CreateInstance during startup, it is not automatically Native-AOT-clean. Hand registration or source generation would be needed for a stronger AOT story. Regular ASP.NET Core deployment does not require AOT, so AOT should not be the sole reason to migrate.

6. Evaluation of Mediator

Mediator is a separate MIT-licensed implementation of the mediator pattern. It uses a Roslyn source generator to generate handler dispatch, DI registrations, and diagnostics rather than discovering handlers with reflection at application startup. Its documented goals include performance, Native AOT support, and build-time detection of missing or multiple request handlers.

As of this report, the repository lists 3.0.2 as the latest stable release and 3.1.0-rc.1 as a prerelease. For production evaluation, pin the stable package first; treat the 3.1 prerelease as a separate experiment.

What Mediator adds

  • Compile-time generated dispatch and DI registration.
  • Diagnostics for missing and multiple request handlers.
  • Explicit no-response contracts such as IRequest and ICommand.
  • Request, command, query, notification, and stream abstractions.
  • Pipeline behaviors, pre-processors, post-processors, and exception handlers.
  • Optional BCL metrics and tracing using System.Diagnostics.Metrics and ActivitySource.

What remains eDMS responsibility

  • Server-authoritative authorization.
  • Immutable audit logging and its failure policy.
  • Transactional boundaries across database and file storage.
  • Durable notification/outbox processing.
  • Correct DI lifetime selection for EF Core-backed handlers.
  • Integration tests proving behavior ordering and security invariants.

6.2 eDMS-specific strengths

Mediator is a better direct candidate for eDMS than the article’s sample in three areas. First, it already models no-response commands. Second, it turns handler discovery and duplicate-handler validation into build-time diagnostics. Third, its source-generated design is materially more suitable if eDMS later needs Native AOT or very low cold-start overhead.

It also supports explicit assembly/type selection, which is useful for eDMS’s layered solution. The source generator belongs in the outermost API project; Mediator.Abstractions belongs alongside messages and handlers. The official guidance warns against installing the source-generator package into every layer of the same deployed artifact.

6.3 eDMS-specific risks

  • Lifetime mismatch: Mediator recommends singleton registration for performance, but eDMS handlers inject IAppDbContext, which is backed by the scoped EF Core AppDbContext. Configure Mediator as Scoped unless handlers are redesigned; otherwise scoped services must not be captured by singleton handlers.
  • ValueTask migration: Mediator’s handler and behavior contracts return ValueTask. Existing eDMS Task-based handlers will need signature changes and the same single-consumption discipline described in the article.
  • Manual behavior registration: standard handlers are generated automatically, but pipeline behaviors still need explicit registration. The exact order of validation, authorization, handler execution, and audit must be encoded and tested.
  • Compile-time configuration: assembly, type, behavior, namespace, lifetime, and telemetry choices are source-generator inputs. The API project must reference the Application message/handler assemblies in a way the generator can see.
  • Release maturity: 3.0.2 is the stable baseline while 3.1.0-rc.1 is prerelease. Pin versions and review generated-code changes during upgrades.
  • Fire-and-forget is intentionally not the default: an open project issue requests explicit fire-and-forget notification support. That is appropriate for safety, but it reinforces that reliable background work belongs in eDMS’s outbox/worker design rather than an ignored publish task.
  • Feature surface: streams, polymorphic notifications, generic handlers, and generated telemetry are useful, but they expand the upgrade and testing surface beyond the small dispatcher needed by eDMS today.

6.4 Maintenance, security, and .NET 10 confidence

The repository’s latest visible main commits and package releases are dated 22 March 2026: stable 3.0.2 and prerelease 3.1.0-rc.1. That is approximately five months without a new upstream commit as of this report. A quiet period is not proof of abandonment, but it lowers confidence in timely security response and ongoing compiler/runtime optimization.

The runtime abstraction itself is small and has less direct attack surface than a network, serialization, authentication, or database library. The source generator and its transitive build dependencies are nevertheless part of eDMS’s software supply chain. “No published advisory” should be treated as “none publicly recorded,” not as a security guarantee.

For .NET 10, include transitive dependency auditing in CI:

dotnet restore
dotnet package list --include-transitive --vulnerable --format json

Also use dependency update automation, an SBOM, package/license review, exact SDK pinning, generated-code compilation tests, and a tested internal fork or migration path. These controls are especially important if Mediator becomes a shared platform dependency.

Assessment: Mediator is the stronger off-the-shelf alternative. It is more compatible with eDMS’s no-response commands and more robust than runtime assembly scanning, but it is not a zero-change swap. The critical proof point is whether the stable generator produces the desired eDMS pipeline and DI wiring with scoped EF Core handlers.

7.1 Recommended shortlist

  1. Immediate.Handlers — first source-generation technical spike because it has a current .NET 10-compatible package and a compile-time call-tree model.
  2. OpenMediatR — compatibility spike when preserving MediatR-shaped APIs and Task-based handlers matters more than AOT.
  3. Mediator — conditional source-generated candidate, subject to the maintenance, security, lifetime, and exact .NET 10 generator gates documented below.
  4. Wolverine — evaluate only when durable messaging, outbox, transports, retries, or workflow capabilities become a real eDMS requirement.

7.2 Common evaluation gates

  • Measure migration effort for one representative query, one mutation, one no-response command, one notification, and one streaming or long-running use case if applicable.
  • Prove scoped IAppDbContext behavior, cancellation, exception propagation, validation order, authorization order, audit timing, and controller integration.
  • Build and test with the exact .NET 10 SDK used by eDMS, including source-generator diagnostics and generated-code review where applicable.
  • Run direct and transitive package vulnerability audits, license review, SBOM generation, and a documented fallback or fork plan before production adoption.
  • Compare representative end-to-end API scenarios and allocations; do not choose a library from a microbenchmark of an empty Ping handler.
Shortlist conclusion: Immediate.Handlers is the strongest new source-generated candidate to investigate, OpenMediatR is the easiest compatibility experiment, and Mediator remains viable with explicit safeguards. Wolverine belongs to a separate durable-messaging decision, not a simple MediatR package swap.

8. Strategic options: fork Mediator or build custom

There are two different meanings of “clone Mediator.” Using the upstream packages behind an eDMS adapter is low-risk. Copying the source, changing the API, and maintaining a permanent fork is a platform decision. A fork should therefore be treated as an organization-owned product, not as a one-time code copy.

CriterionFork/customize MediatorBuild custom dispatcher

eDMS-specific controlHigh, subject to upstream architecture and generator constraints.Very high; every behavior and contract can be designed for eDMS.
Future-project reuseHigh if the organization standardizes the fork and its package/version policy.Uncertain; the small initial scope can grow into an internal framework.
Maintenance burdenUpstream merges, source-generator/compiler compatibility, security fixes, package publishing, and regression testing.All dispatch, diagnostics, AOT, notification, compatibility, and feature maintenance is internal.
AOT readinessAlready designed for source-generated, reflection-free dispatch.Requires substantial investment unless AOT is explicitly out of scope.
Migration riskMedium: API differences, ValueTask, compile-time configuration, and DI lifetime choices remain.High: behaviorally equivalent semantics must be recreated and proven.
Long-term lock-inThe fork becomes the organization’s mediator platform and must track its upstream base.The organization owns the entire platform and its evolution.

8.1 Option 1 — controlled Mediator fork

This is the stronger option when the goal is a reusable internal platform for eDMS and future .NET projects. It reuses a mature feature surface instead of recreating source generation, handler diagnostics, notification publishing, streaming, and AOT support.

  • Keep the upstream repository as a remote and record the exact upstream commit or release used by the fork.
  • Preserve the MIT license, copyright notices, attribution, and licenses of all bundled dependencies.
  • Use organization-owned package and namespace identities if the public API diverges, avoiding ambiguity with upstream Mediator.* packages.
  • Maintain separate packages for abstractions and the source generator, with CI that builds the generator against supported .NET/Roslyn versions.
  • Keep the patch set small and upstreamable where possible; prefer adapters, defaults, and extension points over rewriting generator internals.
  • Publish a compatibility policy, upgrade cadence, security review process, and migration notes for every fork release.

The main risk is that the fork becomes a permanent divergence. Source-generator internals are more difficult to maintain than ordinary application code, and each upstream release can introduce merge conflicts or generated-code changes.

8.2 Option 2 — custom-built dispatcher

A custom dispatcher is appropriate when the required surface is intentionally narrow: request/response dispatch, no-response commands, ordered pipeline behaviors, cancellation, and perhaps a deliberately limited notification mechanism. It gives eDMS exact control over Task versus ValueTask, DI lifetimes, error semantics, and security behavior.

The cost is broader ownership. Even a small implementation eventually needs handler registration guarantees, duplicate detection, diagnostics, test fixtures, AOT decisions, notification failure policy, performance regression tests, documentation, and a compatibility story for future projects. “Custom-built” is not automatically simpler once it becomes a shared platform.

8.3 Recommended sequence

  1. Start with upstream Mediator behind an eDMS-owned IApplicationDispatcher abstraction and validate one complete query and mutation.
  2. Configure scoped lifetime, register the eDMS behaviors explicitly, and prove generated assembly/type discovery in CI.
  3. Fork only if a real requirement cannot be met through configuration, adapters, or behaviors, and only after defining ownership, licensing, release, and upgrade policies.
  4. Choose a fully custom dispatcher only if the team intentionally accepts ownership of the complete internal platform and keeps its feature scope small.
Strategic recommendation: treat Mediator as a conditional candidate rather than an unconditional platform choice. Establish upstream compatibility, security auditing, and .NET 10 CI coverage first. Prefer a controlled fork over a new dispatcher only if the organization accepts responsibility for security response, source-generator compatibility, and release cadence. For eDMS alone, a small custom dispatcher remains viable, but it has the highest risk of expanding into an unplanned framework.

10. Options and recommendation

Keep MediatR

Lowest migration risk

Retains the current integration and avoids writing or maintaining a dispatcher. This remains reasonable if the existing package version and licensing/support policy are acceptable.

Immediate.Handlers

Source-gen candidate

The strongest new technical candidate for a compile-time dispatch spike. It is not a drop-in swap, so the value of generated call trees must justify migrating handler conventions.

OpenMediatR

Compatibility candidate

The lowest-friction alternative to test when preserving MediatR-shaped APIs and Task-based handlers is the priority. It gives up the stronger source-generation/AOT story.

Mediator

Conditional candidate

Use the MIT-licensed Mediator package only with security, maintenance, and exact .NET 10 generator gates. Fork only after a real requirement cannot be solved through configuration or adapters.

Wolverine

Future messaging option

Choose only if eDMS needs durable inbox/outbox, transports, retries, scheduling, sagas, or workflow-oriented messaging. It is not proportionate to today’s in-process dispatcher requirement.

Custom or forked

Highest ownership

Adapt Mukesh’s design or fork Mediator when the organization is willing to own release engineering, security response, compiler compatibility, documentation, and cross-project support.

Preferred recommendation: run one common eDMS vertical-slice spike with Immediate.Handlers, OpenMediatR, and Mediator. Choose Immediate.Handlers if source-generated dispatch materially improves the measured build/runtime profile and the migration cost is acceptable; choose OpenMediatR if API compatibility dominates; choose Mediator if its generator, scoped DI wiring, maintenance posture, and security gates pass. Do not adopt Wolverine unless durable messaging is a confirmed requirement. Choose a custom dispatcher or fork only when the organization explicitly accepts platform ownership.

11. Adoption gates

11.1 Common gates for any alternative

  1. Introduce an eDMS-owned abstraction such as IApplicationDispatcher so controllers and application code do not depend directly on the implementation.
  2. Port and test validation, authorization, audit, caching, and transaction behaviors with their required ordering.
  3. Keep durable notifications and outbox processing separate from the in-process publisher.
  4. Add tests for handler discovery, duplicate detection, no-response commands, cancellation, behavior order, authorization bypass prevention, audit failure handling, and notification failure semantics.
  5. Run the existing backend build, unit tests, integration tests, coverage gate, and representative performance comparisons before removing MediatR.

11.2 Shortlist proof-of-concept gates

  1. Implement the same query, mutation, no-response command, notification, and behavior chain in Immediate.Handlers, OpenMediatR, and Mediator behind the eDMS-owned abstraction.
  2. Record source changes, generated-code changes, package references, startup/build diagnostics, test changes, and migration time for each candidate.
  3. Run dotnet restore, transitive vulnerability auditing, license checks, and exact .NET 10 SDK CI builds for each candidate; reject a package that cannot meet the project’s supply-chain policy.
  4. Compare end-to-end request latency, allocations, cold start, build time, debugging experience, and failure semantics using representative eDMS scenarios rather than an empty-handler microbenchmark.

11.3 Mediator proof-of-concept gates

  1. Reference Mediator.Abstractions from the Application project and install Mediator.SourceGenerator only in the API executable project.
  2. Use stable 3.0.2 and configure options.ServiceLifetime = ServiceLifetime.Scoped because eDMS handlers use scoped EF Core services.
  3. Configure explicit message assemblies/types and an explicit ordered behavior list; inspect the generated Mediator.g.cs output.
  4. Port one query and one mutation, including ValidationBehavior, AuthorizationBehavior, and AuditLoggingBehavior.
  5. Confirm that no-response commands, cancellation, FluentValidation error aggregation, and controller injection behave exactly as before.
  6. Compare build diagnostics, test coverage, startup behavior, allocations, and representative request latency against the current MediatR implementation.

11.4 Mukesh dispatcher proof-of-concept gates

  1. Implement both response and no-response command contracts, or explicitly standardize all no-response commands on Unit.
  2. Keep Task initially unless representative benchmarks demonstrate a meaningful benefit from ValueTask.
  3. Scan the Application assembly explicitly; reject duplicate request handlers and missing registrations during startup.
  4. Port the same eDMS behaviors and verify equivalent failure and cancellation semantics.
Migration principle: the success criterion is behavioral equivalence and preserved security guarantees, not simply achieving a lower nanosecond number in the dispatcher microbenchmark.

12. Conclusion

The article’s dispatcher is a credible custom baseline, but it should be evaluated alongside real alternatives rather than treated as the default replacement. It is understandable and potentially fast, yet eDMS would own every compatibility, security, diagnostics, notification, AOT, and future-project concern.

Immediate.Handlers is the strongest new source-generated candidate to investigate; OpenMediatR is the easiest compatibility experiment; and Mediator remains a technically strong but maintenance-sensitive option. Wolverine is valuable when the problem becomes durable messaging, not when the problem is only in-process request dispatch. Foundatio.Mediator, DispatchR, and ModernMediator are worth monitoring or selectively spiking, but their smaller ecosystems and differing conventions raise adoption risk.

Across all candidates, the decisive work is not the dispatcher lookup. It is preserving server-authoritative authorization, immutable audit logging, handler compatibility, assembly correctness, transaction boundaries, durable notification behavior, and the existing test guarantees.

Final assessment: run a common vertical-slice comparison of Immediate.Handlers, OpenMediatR, and Mediator; retain MediatR if migration value is not demonstrated; reserve Wolverine for a durable-messaging decision; and choose a custom dispatcher or fork only with explicit platform ownership, security response, release, and upgrade commitments.
