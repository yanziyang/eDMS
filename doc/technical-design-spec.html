1. Introduction & Purpose

The functional spec answers what eDMS does and why. This document answers how it is built: solution structure, physical database schema, class/interface-level design, request flows, deployment topology, testing strategy, and coding conventions.

Where the functional spec already fixes a decision — tech stack (FS §3), data model (FS §8), API surface (FS §10), permission algorithm (FS §9) — this document treats that as given and adds the implementation layer underneath it.

1.1 How to use this document

  • Building the backend? Start at §5 and §6.
  • Building the frontend? Start at §7.
  • Wiring CI/CD or an environment? Start at §11.
  • Writing tests? Start at §12.

2. Architecture Overview

2.1 Architectural style

eDMS is a modular monolith: one ASP.NET Core Web API process, one PostgreSQL database, one React SPA — not a microservices decomposition. This matches the scale in the functional spec (single organization, growing to dozens of sites, no stated requirement for independent team deployability). The backend is internally layered using Clean Architecture (Domain → Application → Infrastructure/API, FS §12.1), preserving a future service-extraction path without over-engineering toward it now.

Within the Application layer, use cases follow a CQRS-lite pattern — commands and queries as discrete objects dispatched through MediatR — so authorization, validation, and audit-logging attach per use case via pipeline behaviors instead of being duplicated per controller action.

2.2 System context & containers

System context: the API is the only component that talks to Postgres, file storage, or SMTP — and the only one that enforces authorization.

2.3 Backend layering (dependency direction)

Domain has zero project references. Application references only Domain. Infrastructure and Api reference inward. A CI architecture test (§13.1) fails the build if this is violated.

ADR-8 implementation rules (normative):

  1. Use one migrations assembly per provider (eDMS.Infrastructure.Migrations.Postgres|SqlServer|MySql|Sqlite); select it at runtime with MigrationsAssembly(...) and in tooling with -p <project> plus Database__Provider=<provider>.
  2. Quarantine provider-specific schema in AppDbContext.ApplyProviderSpecificColumnTypes: Postgres keeps citext, jsonb, and now(); SQLite uses NOCASE and application-set timestamps; SQL Server/MySQL use native case-insensitive collations and UTC defaults.
  3. SQLite has no native DateTimeOffset; apply DateTimeOffsetToBinaryConverter for SQLite only.
  4. Do not use provider-specific LINQ. Replace Npgsql-only EF.Functions.ILike with portable ToLower().Contains().
  5. SQLite is a development convenience, not a production target; its gitignored edms-dev.db uses portable search behavior while Postgres keeps the tsvector migration.
  6. The host applies the development default (Development with no provider config ⇒ Sqlite, otherwise Postgres); infrastructure remains environment-agnostic.

5. Backend Technical Design

5.1 Domain layer

Base types remove repetition across entities:

public abstract class AuditableEntity
{
    public Guid Id { get; protected set; }
    public Guid CreatedBy { get; protected set; }
    public DateTimeOffset CreatedAt { get; protected set; }
}

public abstract class SoftDeletableEntity : AuditableEntity
{
    public bool IsDeleted { get; private set; }
    public DateTimeOffset? DeletedAt { get; private set; }
    public Guid? DeletedBy { get; private set; }

    public void MarkDeleted(Guid byUserId, DateTimeOffset at) { /* ... */ }
    public void Restore() { /* ... */ }
}

Document, Folder, Site, Library derive from SoftDeletableEntity. DocumentVersion, SitePermission, ItemPermission, AuditLogEntry derive from AuditableEntity only — versions are immutable, permissions are removed outright, audit entries are immutable (FR-AUDIT-04). Domain entities own their invariants — e.g. Document.CheckOut(userId) throws if already checked out by someone else, rather than trusting every caller to re-check.

5.2 Application layer

Pattern for every use case, illustrated with check-out (FR-VER-05):

public sealed record CheckOutDocumentCommand(Guid DocumentId) : IRequest<Result>;

public sealed class CheckOutDocumentHandler(
    IAppDbContext db, ICurrentUser currentUser, IPermissionResolver permissions, IAuditLogger audit)
    : IRequestHandler<CheckOutDocumentCommand, Result>
{
    public async Task<Result> Handle(CheckOutDocumentCommand cmd, CancellationToken ct)
    {
        var document = await db.Documents.FindAsync([cmd.DocumentId], ct)
            ?? throw new NotFoundException(nameof(Document), cmd.DocumentId);

        await permissions.RequireAsync(currentUser.UserId, ObjectType.Document, document.Id, PermissionLevel.Contribute, ct);

        document.CheckOut(currentUser.UserId);
        await db.SaveChangesAsync(ct);
        await audit.LogAsync(AuditAction.CheckOut, ObjectType.Document, document.Id, document.Name, ct);
        return Result.Success();
    }
}

MediatR pipeline behaviors, applied to every command/query in this order:

  1. ValidationBehavior — runs the FluentValidation validator; short-circuits with 400 on failure.
  2. AuthorizationBehavior — for any IAuthorizableRequest, calls IPermissionResolver before the handler runs. This is what makes "every mutating endpoint enforces the permission model" structurally true rather than aspirational.
  3. AuditLoggingBehavior — for any IAuditableRequest, writes the audit entry after a successful handler run. FR-AUDIT-01's action list is complete by construction, not by developers remembering to log at each call site.

5.3 IPermissionResolver — the resolution algorithm (FS §9)

public interface IPermissionResolver
{
    Task<PermissionLevel> GetEffectiveLevelAsync(Guid userId, ObjectType type, Guid objectId, CancellationToken ct);
    Task RequireAsync(Guid userId, ObjectType type, Guid objectId, PermissionLevel required, CancellationToken ct);
}
  • Bypass: ICurrentUser.IsSystemAdmin short-circuits to Full Control immediately — but the audit-logging step still runs, so admin bypass is always audited.
  • Caching: effective-permission lookups cached in IMemoryCache, keyed by (userId, objectType, objectId), 30s TTL. Any mutation of ItemPermission/SitePermission/GroupMember invalidates descendants in the same handler, right after SaveChangesAsync. Bounds staleness to 30s even if an invalidation path is missed. Revisit with Redis only if the API scales beyond one instance.

The physical hierarchy walk is a single recursive CTE — see §6.3.

5.4 IFileStorageProvider and versioning

Storage key convention: {StorageRoot}/{siteId}/{libraryId}/{documentId}/{versionId}/{originalFileName}.

Upload flow (backing FR-DOC-01 / FR-VER-01):

  1. Compute SHA-256 while streaming to a temp file — avoids buffering the full 250 MB ceiling in memory.
  2. Sniff content-type from magic bytes (not the client header) and reject blocked/oversized files (FR-DOC-03).
  3. Same name already exists in the folder? Create a new DocumentVersion, update CurrentVersionId. Otherwise create a new Document at v1.0.
  4. Move the temp file to its final key only after the DB transaction commits — avoids orphaned blobs on a failed transaction; an hourly sweep (§5.8) cleans up any that slip through.

5.5 Authentication implementation

  • User store: ASP.NET Core Identity (ApplicationUser : IdentityUser<Guid>) — password hashing, lockout tracking (backs FR-AUTH-06). IsSystemAdmin is a plain bool, not an Identity Role.
  • Access token: JWT, RS256, 15 min default. Claims: sub, email, is_admin, jti. Key pair from environment/secret store — never committed.
  • Refresh token: opaque 256-bit value; only its SHA-256 hash is persisted. Delivered as an httpOnly, Secure, SameSite=Strict cookie — never touched by frontend JS.

Table not in FS §8.2 (auth plumbing, not a domain entity):

CREATE TABLE refresh_tokens (
    id                uuid PRIMARY KEY,
    user_id           uuid NOT NULL REFERENCES "AspNetUsers"(id),
    token_hash        text NOT NULL UNIQUE,
    expires_at        timestamptz NOT NULL,
    created_at        timestamptz NOT NULL DEFAULT now(),
    created_by_ip     text,
    revoked_at        timestamptz,
    replaced_by_token_id uuid REFERENCES refresh_tokens(id)
);
Reuse detection: if a revoked refresh token is ever presented again — a signal of token theft/replay — the entire token chain for that user is revoked and re-authentication is forced. This is why the schema keeps a replaced_by_token_id chain instead of just an is_revoked flag.

SAML2 / OIDC (P3): both terminate at a callback endpoint that performs JIT provisioning, then calls the same ITokenService.IssueTokenPairAsync local login uses. The SPA's auth handling never needs to change when SSO ships.

5.6 Authorization implementation — two layers

  1. Coarse, policy-based: [Authorize] / [Authorize(Policy = "SystemAdmin")] — cheap, no DB round-trip, filters traffic before MediatR.
  2. Fine, resource-based: the AuthorizationBehavior (§5.2) backed by IPermissionResolver (§5.3) — implements the actual hierarchy walk, which can't be a static ASP.NET Core policy since the required level depends on which specific object the request targets.

5.7 API layer

One controller per aggregate root area, thin — constructs a MediatR request, sends it, maps the result. No business logic in controllers.

6. Database Technical Design

6.1 Conventions

  • snake_case in Postgres, PascalCase in C#, bridged by EFCore.NamingConventions — DDL below shows the physical (snake_case) truth.
  • Primary keys: uuid, generated app-side (§4), not gen_random_uuid() — testable without a DB round-trip.
  • citext extension for AspNetUsers.email case-insensitive uniqueness.
  • Every FK is ON DELETE RESTRICT by default; intentional cascades are called out explicitly.

6.2 Core physical schema

Full field semantics are in FS §8.2; this is the DDL for Phase 1 tables. P2 tables (content types, share links, alerts, favorites) follow the same conventions when that phase begins.

6.3 The permission-hierarchy query

A single recursive CTE resolves the nearest unique ACL up the Folder → Library → Site chain in one round trip instead of N+1 queries:

WITH RECURSIVE chain AS (
    SELECT :object_type AS object_type, :object_id AS object_id, 0 AS depth
    UNION ALL
    SELECT
        CASE WHEN f.parent_folder_id IS NOT NULL THEN 1 ELSE 0 END,
        COALESCE(f.parent_folder_id, f.library_id),
        c.depth + 1
    FROM chain c
    JOIN folders f ON c.object_type = 1 AND f.id = c.object_id
    WHERE c.depth < 20   -- matches FR-FLD-06's max nesting
)
SELECT object_type, object_id, depth FROM chain ORDER BY depth;

The resolver walks the result in order, stopping at the first level with an item_permissions row for the caller (direct or via group membership); falls through to site_permissions at the end.

6.4 Migrations

EF Core Code-First uses one migration set per database provider (ADR-8), each in its own project so a database never sees another provider's migrations. Select the set with Database__Provider and the matching -p project:

# bash — PostgreSQL (production):
Database__Provider=Postgres dotnet ef migrations add <Name> -p server/src/eDMS.Infrastructure.Migrations.Postgres -s server/src/eDMS.Api
# PowerShell:
#   $env:Database__Provider='Postgres'; dotnet ef migrations add <Name> -p server/src/eDMS.Infrastructure.Migrations.Postgres -s server/src/eDMS.Api
# SqlServer / MySql / Sqlite: swap the value and project accordingly.

Every model change requires a migration in all four sets; verify none is missed with dotnet ef migrations has-pending-model-changes -p <project> -s server/src/eDMS.Api per provider. Auto-apply on startup remains limited to Development/Testing; every other environment runs migrations as an explicit CI/CD step before the new API version deploys (§11.3) — never auto-migrate production from application startup.

6.5 Seed data

First run against an empty database creates exactly one System Administrator from configuration (Seed:AdminEmail/Seed:AdminTempPassword, required env vars, no baked-in default), forced password reset on first login. No sample content is seeded outside local dev — docker-compose.yml (§11.2) seeds demonstration data matching prototype(html)/assets/data.js.

7.3 API client

One typed wrapper, not per-feature fetch calls, so the 401→refresh→retry flow (§9.1) is implemented exactly once:

let accessToken: string | null = null;
let refreshPromise: Promise<void> | null = null;

async function request<T>(path: string, init: RequestInit = {}): Promise<T> {
  const res = await fetch(`${API_BASE}${path}`, {
    ...init,
    credentials: "include",   // sends the httpOnly refresh cookie
    headers: { ...init.headers, ...(accessToken && { Authorization: `Bearer ${accessToken}` }) },
  });
  if (res.status === 401 && !path.startsWith("/auth/")) {
    refreshPromise ??= refreshAccessToken().finally(() => (refreshPromise = null));
    await refreshPromise;         // concurrent 401s de-dupe to one refresh call
    return request<T>(path, init);
  }
  if (!res.ok) throw await ApiError.fromResponse(res);
  return res.status === 204 ? (undefined as T) : res.json();
}

accessToken lives in module memory only — never localStorage. An XSS payload that can read localStorage can read a token stored there; keeping it in memory costs one silent refresh call on page reload and closes that gap.

9. Key Flows

Sequence diagrams for the two flows with the most implementation nuance. Upload/versioning and search request flows are diagrammed in technical-design-spec.md §9.2 (Mermaid) — omitted here to keep this page focused.

9.1 Local login, silent refresh, and 401 recovery

A 401 triggers exactly one de-duped refresh call, then the original request is retried once with the new access token.

9.2 Permission-checked request (AuthorizationBehavior)

The permission check runs before the handler on every mutating command — there is no code path that reaches business logic without it.

10. Security Design

Authorization is server-authoritative. The SPA's route guards, disabled buttons, and hidden menu items (§7.2) are UX polish. The AuthorizationBehavior (§5.2, §5.6) is the only thing that decides whether a mutation is allowed, on every command, with no opt-out short of the explicit marker used only for /auth/login, /auth/forgot-password, /auth/reset-password.

10.1 Transport & secrets

TLS terminated at the reverse proxy; Kestrel does not hold the certificate above local dev. Strict-Transport-Security added in non-dev environments. Secrets come from environment variables / the host's secret manager (§11.4) — never from committed appsettings.json. Local dev uses dotnet user-secrets.

10.2 Input validation & file safety

Every command/query has a FluentValidation validator — no endpoint skips validation "because the frontend already checks it." File content-type is sniffed from magic bytes server-side, independent of the client header. IFileStorageProvider.SaveAsync has a pluggable IAntivirusScanner hook (no-op in MVP) so a ClamAV integration later is a new DI registration, not a call-site change.

10.3 Rate limiting & lockout

/auth/login and /auth/forgot-password: 10 req/min/IP. Account lockout after 5 failed logins, 15-minute cooldown (FR-AUTH-06) — enforced by ASP.NET Core Identity's built-in tracking, not reimplemented.

10.4 Audit logging

The AuditLoggingBehavior writes after the handler's transaction commits, as a separate SaveChangesAsync call. A failure to write the audit row does not roll back the business mutation — an audit outage shouldn't stop the product — but is itself logged at Error so an audit gap stays operationally visible.

12.1 Backend

12.2 Frontend

LayerToolCovers
Unit/componentVitest + React Testing Library + MSWPages, feature API clients, auth context, and api-client.ts refresh/retry logic in jsdom with mocked HTTP. 90% line/statement/function/branch thresholds apply to src, excluding generated UI, wiring, and types.
E2EPlaywrightLogin → browse → upload → check-out/in → share → search against the full docker-compose stack. E2E_DATABASE_PROVIDER selects Postgres (default) or SQLite, and the harness resets the E2E database before each run.

12.3 Non-negotiable test cases

  • Permission resolution is correct at every hierarchy point (unique ACL per level, Site inheritance, group-derived grants, additive-across-groups).
  • Refresh-token reuse detection actually revokes the full chain.
  • Soft-deleted rows never appear in a default query (the global filter is easy to bypass by accident with a leftover IgnoreQueryFilters()).
  • An audit entry is written for every FR-AUDIT-01 action — one parameterized test over the action enum, so a newly added action can't be forgotten.

13. Coding Standards & Conventions

13.1 C# / .NET

  • Nullable reference types enabled solution-wide; a possible-null-dereference warning is an error in CI.
  • File-scoped namespaces, primary constructors for DI, sealed by default.
  • Project-reference direction (§2.3) enforced by a CI architecture test (e.g. NetArchTest.Rules asserting Domain has no outward dependencies) — a rule stated only in prose gets violated eventually.

13.2 TypeScript / React

  • strict: true; no any without an inline comment explaining why.
  • Function components + hooks only.
  • ESLint + Prettier, both blocking in CI, not editor-only suggestions.
  • Test files co-located next to the component they test, not in a parallel tree.

13.3 Git workflow

  • Trunk-based: short-lived feature branches off main, merged via PR with required green CI.
  • Conventional Commits style (feat:, fix:, refactor:) — convention now, tooling-enforced changelog generation later.
  • No direct pushes to main; branch protection requires review + green CI.
